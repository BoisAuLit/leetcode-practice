# 设计题通用清单（Design Problem Checklist）

> 设计题没有算法可背 —— 它考的是**三个问题**：
> **① 两次调用之间我必须记住什么？② 哪个操作必须最快？③ 边界语义是什么？**
> 这份清单把这三问拆成可执行的步骤。

---

## 一、开场五步（面试里按这个顺序走）

### 第 1 步：把 API 抄下来，标出每个方法的**调用频率**

```
LRUCache(capacity)        —— 一次
get(key)                  —— 极频繁   ⟸ 必须 O(1)
put(key, value)           —— 极频繁   ⟸ 必须 O(1)
```

**为什么先看频率？** 因为它决定了**成本往哪边挪**：

| 情形 | 策略 | 本专题的例子 |
|---|---|---|
| **查询频繁、更新稀少** | 把工作挪到**更新**时 | LC-1396（增量 sum/count）、LC-0348（增量行列计数） |
| **更新频繁、查询稀少** | 把工作挪到**查询**时（懒清理） | LC-1797（懒清理过期）、LC-0362 |
| **两者都频繁** | 必须用**两个数据结构**组合 | LC-0146、LC-0460、LC-0380 |
| **某个操作太贵** | 把成本挪到别的操作 | LC-1146（snap O(1)，代价是 get O(log k)） |

### 第 2 步：问「**两次调用之间，我必须记住什么？**」

这一句定了，字段就定了，代码只是搬运。

| 题 | 必须记住的状态 |
|---|---|
| LC-0158 read4 II | **未交付的缓冲字符** `buf4[i:cnt]` |
| LC-1472 Browser History | 历史数组 + **游标** + **有效长度** |
| LC-1396 Underground | **在途乘客** + 每条线路的 `(sum, count)` |
| LC-0146 LRU | 双向链表（顺序）+ 字典（定位） |
| LC-0460 LFU | 三张表 + **`min_freq` 指针** |
| LC-1797 Auth Manager | token -> **过期时刻**（不是生成时刻） |
| LC-1146 Snapshot | 每个 index 一条**版本链** + 当前 snap_id |

### 第 3 步：确认**边界语义**（最容易错的地方）

- 不等号是 `<` 还是 `<=`？**拿官方样例的边界时刻手算一遍。**
- 失败的操作要不要**改变状态**？（通常：**不要**）
- 容量为 0 / 空集合 / 不存在的 key，各自返回什么？

### 第 4 步：先写出**朴素正确**的版本，再优化

面试里先说「我可以用 O(n) 的做法，这样…… 然后我们可以优化到 O(1)，方法是……」
**比直接写最优解分更高** —— 它展示了推理过程。

### 第 5 步：**诚实**说明复杂度

- 哈希表是**平均** O(1)，不是最坏 O(1)
- 均摊（amortized）O(1) 和最坏 O(1) 要分清
- 不要把所有操作一律写成 O(1)

## 二、六个反复出现的套路

### ① 两个结构组合（一个负责顺序/随机，一个负责定位）

**字典几乎总是那个「负责定位」的角色。**

| 题 | 负责顺序/随机 | 负责定位 |
|---|---|---|
| LC-0146 LRU | 双向链表 | `key -> node` |
| LC-0460 LFU | 按 freq 分桶的有序结构 | `key -> val` + `key -> freq` |
| LC-0380 GetRandom | **紧凑数组** | `val -> 下标` |
| LC-0381 GetRandom 重复版 | 紧凑数组 | `val -> 下标**集合**` |

### ② swap-with-last（把 O(n) 删除变成 O(1)）

```python
arr[i] = arr[-1]      # ! 把最后一个搬进坑
arr.pop()             # ! O(1)
```
**前提**：不关心顺序。**收益**：数组保持紧凑 ⟹ 随机访问仍均匀。
📍 LC-0380、LC-0381

### ③ 逻辑删除 / 有效长度（不真删，只标记不可达）

```python
self.last = self.cur      # ! 之后的内容逻辑上不可达，O(1)
```
比 `del arr[i+1:]`（O(n)）好。📍 LC-1472

### ④ 懒清理（Lazy Cleanup）

**不主动删过期项，只在读取时过滤或清理。**
**正确性前提**：时间/版本**单调不减** ⟹ 过期的**永远不会复活**。
📍 LC-1797、LC-0362、LC-0933

### ⑤ 增量聚合（Incremental Aggregation）

**不存明细，只存标量。**
```python
self.sum += x; self.count += 1       # ! 更新时 O(1)
avg = self.sum / self.count          # ! 查询时 O(1)
```
✅ 适用于**和、计数、平均值、最大值、最小值**。
❌ **不适用于中位数、分位数**（需要有序结构 ⟹ 双堆，见 `09-heap`）。
📍 LC-1396、LC-0348

### ⑥ 懒删除堆（Lazy Deletion Heap）

当堆里的条目会**被更新**（变成陈旧数据）时：
```python
while heap and is_stale(heap[0]):
    heappop(heap)                    # ! 只在读堆顶时清理
```
**不变量**：**只保证清理后的堆顶有效**，堆里仍可能躺着垃圾。
📍 LC-1797 解法 3、`14-intervals` 的 LC-1851、`09-heap` 的 LC-0480

## 三、通用边界清单（每道设计题都过一遍）

| # | 边界 | 为什么 |
|---|---|---|
| 1 | **容量 / 长度为 0** | LC-0460 不特判会在空桶上 `popitem` ⟹ `KeyError` |
| 2 | **容量为 1** | 每次插入都触发淘汰 |
| 3 | **操作不存在的 key** | 必须返回哨兵值，且**不改变任何状态** |
| 4 | **put 已存在的 key** | 这是**更新**不是插入 ⟹ **不能触发淘汰** |
| 5 | **删到一个都不剩** | 空集合要不要删 key？（LC-0381：**要**） |
| 6 | **恰好在边界时刻** | `expiry == now` 算活还是死？（LC-1797：**死**） |
| 7 | **失败操作的幂等性** | 被拒绝的调用必须**不留痕迹**（LC-1797 的 renew） |
| 8 | **重复调用同一操作** | 顺序 / 计数会不会错乱 |
| 9 | **状态清理** | `checkOut` 后必须删掉在途记录（LC-1396），否则内存泄漏 |
| 10 | **Stateful API 序列测试** | 单个方法对 ≠ 序列对。**必须用随机操作序列对拍** |

## 四、Stateful API 怎么测（本专题的测试方法）

**单独测每个方法是不够的** —— 设计题的 bug 几乎总是出在**操作序列**上。

本专题每道新题的测试都包含：

1. **官方样例**（逐步断言）
2. **逐项边界**（上面那张清单）
3. **随机操作序列对拍**：
   ```python
   for _ in range(3000):
       ops = 随机生成一串 (方法名, 参数)
       outs = [跑一遍每种实现，收集返回值序列 for 每种实现]
       assert 所有实现的返回序列完全一致
   ```
4. **独立真值（reference implementation）**：
   再用**最朴素、最贴近题目定义**的方式算一遍，和上面比。
   —— 三个优化实现互相一致还不够，**它们可能一起错**。

> **LC-0381 的下标集合顺序 bug 就是随机对拍抓出来的** ——
> 官方样例和手写的边界用例全部通过，只有随机序列能触发
> 「要删的值恰好等于末尾元素的值」这个组合。

## 五、复杂度用词的精确含义

| 说法 | 含义 | 本专题的例子 |
|---|---|---|
| **最坏 O(1)** | 任何单次调用都是常数 | LC-0380 的 `getRandom`（纯数组访问）；双向链表的插删 |
| **平均 O(1)** | 哈希表的期望；最坏可能退化 | 所有用 `dict` / `set` 的定位操作 |
| **均摊 O(1)** | n 次操作总共 O(n)，单次可能更贵 | LC-1472 双栈版的 `visit`；LC-1797 的计数时清理 |
| **O(log n)** | 有序结构 / 二分 / 堆 | LC-1146 的 `get`；懒删除堆的操作 |

⚠️ **面试里把「平均」说成「最坏」是会被追问的。**
正确说法：「`get` 和 `put` 都是 **O(1) 平均**，因为底层是哈希表；
链表操作本身是最坏 O(1)。」

## 六、本专题的跨专题设计题

很多经典设计题的**主归属在别的专题**（因为那里的算法才是考点）：

| 题 | 实体在 | 为什么不在 Design |
|---|---|---|
| LC-0155 Min Stack | `04-stack-queue` | Stack 的辅助状态是 Stack 专题的内容 |
| LC-0622 Design Circular Queue | `04-stack-queue` | 环形缓冲属于 Queue |
| LC-0981 Time Based KV Store | `05-binary-search` | 考点是**二分找版本** |
| LC-0208 Implement Trie | `08-tries` | 考点是 Trie 本身 |
| LC-0295 Find Median from Data Stream | `09-heap` | 考点是**双堆** |
| LC-0355 Design Twitter | `09-heap` | 考点是 k 路合并 |
| LC-3408 Design Task Manager | `09-heap` | 考点是动态优先级 + 懒删除 |
| LC-0729 My Calendar I | `14-intervals` | 考点是**区间重叠判定** |
| LC-0380 Insert Delete GetRandom | `01-arrays-hashing` | 考点是 **Array + Hash Map** |
| LC-0073 / LC-0289 的原地编码 | `01-arrays-hashing` / `15-math-geometry` | 考点是矩阵原地修改 |

> **「这是不是设计题」不取决于 API 的形状，而取决于
> 「解开它需要的那个关键洞察属于哪个领域」。**
